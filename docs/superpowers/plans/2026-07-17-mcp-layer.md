**Goal:** Expose the RAG pipeline as an **MCP server** so any MCP-capable agent (Claude Desktop, Claude Code, custom agents, or Anthropic's API MCP connector) can ingest a corpus and ask citation-grounded questions over it — a *third entrypoint* over the same in-process NestJS services, alongside the HTTP API (GO-21a–d) and the CLI (GO-21h). No pipeline logic is duplicated; the MCP server is a thin protocol adapter, exactly as the CLI is.

**Why this milestone:** It turns the project from "a RAG app" into "a retrieval *tool* an agent can call." That is the strongest strategic signal in the roadmap (see `DESIGN_DECISIONS.md` D8 for the multi-agent context this feeds). It also exercises the same architectural thesis the rest of the project sells: clean seams, owned code, no framework lock-in.

## 1. Architecture — a third entrypoint, not a new pipeline

The load-bearing constraint (mirrors the CLI, GO-21h / `cli` skill): the MCP server **resolves the existing services from a NestJS application context and calls them in-process** — no HTTP hop, no re-implemented chunking/retrieval/generation.

```
                         ┌───────────────────────────────┐
   HTTP  (controllers) ─▶│                               │
   CLI   (commander)   ─▶│  IngestionService             │
   MCP   (this doc)    ─▶│  GenerationService            │─▶ Retrieval → pgvector
                         │   (retrieve → abstain → gen)  │─▶ Voyage / Anthropic adapters
                         └───────────────────────────────┘
```

- **Entrypoint:** `src/mcp/main.ts` — boots `NestFactory.createApplicationContext(AppModule, { logger: false })` (same pattern as `eval/run-eval.ts` and `src/cli/main.ts`), resolves `IngestionService` and `GenerationService`, and hands them to the MCP server wiring. Logging stays on Nest's structured logger (rule `coding-standards.md`) — but MCP over stdio means **stdout is the protocol channel**, so all logs MUST go to **stderr** (see §5, Open Decision D3).
- **No business logic in the MCP layer.** It maps MCP tool calls → service calls → MCP results. The abstain policy, citation mapping, and provider selection all stay where they already live (`GenerationService` + adapters). This is the same "controllers are thin" rule (`coding-standards.md`) applied to a new transport.

## 2. Tool surface

Two tools, matching the two things the pipeline does. Keep the surface minimal — a small, well-described tool set is a documented best practice (fewer tools → better model tool selection).

### `rag_query` (the headline tool)
- **Description (drives model tool-selection):** be prescriptive about *when* to call it — e.g. *"Answer a question using only the ingested document corpus, returning a grounded answer with citations to source passages. Call this when the user asks something that the corpus would contain; it returns 'not in the corpus' rather than guessing."*
- **Input:** `{ question: string }`.
- **Output:** the `QueryResult` shape already returned by `POST /query` — `{ answer, citations[], chunks[], citationsSupported }` — serialized into MCP result content (see §4 for the citation-mapping detail and §5 D1 for structured-vs-text).
- **Abstain path is preserved for free:** it lives in `GenerationService` above the provider, so an out-of-corpus question returns the verbatim "not in the corpus" answer with `citations: []`. The MCP tool must surface that honestly, not as an error.

### `rag_ingest` (secondary; gate behind a decision)
- **Description:** *"Chunk, embed, and index the documents under a filesystem path into the corpus (idempotent)."*
- **Input:** `{ path: string }`.
- **Output:** the ingest stats (`{ docs, chunks, ms }`).
- ⚠️ **Exposing filesystem ingestion to an arbitrary agent is a capability/security decision** — see §5 D2. Default recommendation: expose it, but make it opt-in via an env flag (`MCP_ENABLE_INGEST`, default `false`), so the shipped server is query-only unless an operator turns writes on.

**Resources/prompts (out of scope for v1):** MCP also supports "resources" (readable context) and "prompts" (templates). We could later expose the corpus's source documents as MCP *resources*. Not in v1 — tools are the whole value here.

## 3. Transport

MCP defines two transports; we should support both, because they serve the two consumers:

| Transport | Who uses it | Notes |
|-----------|-------------|-------|
| **stdio** | Local agents — Claude Desktop, Claude Code, `npx` spawns | The server is a subprocess; JSON-RPC over stdin/stdout. **stdout is reserved for the protocol** — logging must go to stderr. This is the primary/default transport. |
| **Streamable HTTP** | Remote agents, and **Anthropic's API MCP connector** | The connector consumes a `{type: "url", url, name}` server over **Streamable HTTP** (confirmed via `claude-api` reference). SSE-only transport is deprecated in the MCP spec — implement Streamable HTTP, not legacy SSE. |

**Recommendation:** ship **stdio first** (v1 — unblocks Claude Desktop/Code, the cheapest win), add **Streamable HTTP** in a follow-up sub-task so the same server is reachable by the API MCP connector and remote agents. Selecting the transport via an env var (`MCP_TRANSPORT=stdio|http`) keeps the entrypoint single.

## 4. The hard part — mapping our citations into MCP results

This is the one piece with real design content; everything else is plumbing.

- Our `AnthropicGenerationProvider` returns native Claude citations as **`char_location` spans** (`cited_text`, `document_index`, `start_char_index`/`end_char_index`) already mapped back to the source chunk (`{ content, source, score }`). `QueryResult.citations` is our own normalized shape over that.
- MCP tool results are content blocks (text, and — in current spec revisions — structured/JSON content). **MCP has no first-class "citation" type**, so we must decide how the grounding survives the protocol boundary:
  1. **Structured content** — return `{ answer, citations, chunks, citationsSupported }` as JSON so a programmatic agent can render citations itself. Preferred for agent consumers.
  2. **Human-readable text** — a formatted answer with inline `[n]` markers and a trailing source list, for agents/clients that only render text.
  3. **Both** — structured content + a text fallback. This is the honest, no-information-lost option and the recommended target.
- **Non-citation providers** (the `openai-compatible` adapter, `supportsCitations: false`) must surface `citationsSupported: false` and `citations: []` through MCP — **never fabricate a citation** to fill the field. This is the same rule as everywhere else (`ai-and-secrets.md`); the MCP layer inherits it because it reads `QueryResult`, it doesn't re-derive citations.

**Open sub-problem:** the exact MCP result schema for "answer + citations" depends on the `@modelcontextprotocol/sdk` version's structured-content support. Pin this against the installed SDK at build time (see §6) before finalizing the `rag_query` return shape.

## 5. Open decisions (resolve before slicing into build tasks)

- **D1 — Result shape for `rag_query`:** structured content, formatted text, or both? *Recommendation: both (structured + text fallback).* Confirm the SDK's structured-content API first.
- **D2 — Expose `rag_ingest` at all, and if so, guarded how?** Writing to the corpus from an agent call is a capability grant. *Recommendation: ship it behind `MCP_ENABLE_INGEST=false` by default; query-only out of the box.*
- **D3 — Logging under stdio:** structured logs must not corrupt the stdout JSON-RPC stream. *Recommendation: route the Nest logger to stderr when `MCP_TRANSPORT=stdio`.* This is a hard correctness requirement, not a preference.
- **D4 — Auth for the HTTP transport:** the stdio server trusts its parent process; a Streamable HTTP server is network-exposed. For the API MCP connector, auth is a bearer `authorization_token` on the server declaration (and, in the Managed Agents surface, credentials come from a vault — never inline). *Recommendation: v1 stdio has no auth (parent-process trust); HTTP transport ships with a bearer-token check, secret via env only (`ai-and-secrets.md`).*
- **D5 — Does this need an eval?** MCP is a transport over the *existing* retrieval/generation path — it doesn't change chunking, `k`, `MIN_SCORE`, embeddings, or index params, so **no `npm run eval` is required** (rule `evals.md`; same reasoning as the CLI). An `answer-eval` pass is worthwhile once `rag_query` is wired, to confirm grounding/abstain survive the new serialization (mirrors the generation-provider note in `tasks.md`).

## 6. Dependencies & guardrails

- **New dependency:** `@modelcontextprotocol/sdk` (the official TypeScript MCP SDK). This is a **protocol** SDK, not a RAG framework — it does not violate the "no LangChain/LlamaIndex" rule (`coding-standards.md`); it's the MCP equivalent of `commander` for the CLI. Confirm the current `McpServer` / tool-registration / transport API **against the installed package version at build time** — do not code the tool-registration or transport calls from memory; the SDK surface drifts.
- **Config via `@nestjs/config`** — `MCP_TRANSPORT`, `MCP_ENABLE_INGEST`, and any HTTP-transport port/token are env-driven with sane defaults; no magic constants (`coding-standards.md`).
- **Codemap + tests:** new module/entrypoint/symbols → update `doc/codemap.md` in the same change (`coding-standards.md`); unit-test the tool-call → service-call mapping (mock the services) and the citation serialization; a `LEARNINGS.md` entry per slice.

## 7. Proposed build slices (fill in when accepted)

Rough shape — to be decomposed into `RAG-65a…` with concrete "done when" tests:

1. `src/mcp/main.ts` app-context bootstrap + service resolution (no tools yet) — *done when the process starts and cleanly shuts down.*
2. `rag_query` tool over **stdio**, structured + text result, abstain preserved — *done when a stdio MCP client gets a cited answer and a correct abstain.*
3. Citation serialization + unit tests (both provider types) — *done when `citationsSupported:false` returns `[]` and never fabricates.*
4. `rag_ingest` tool behind `MCP_ENABLE_INGEST` — *done when ingest works with the flag on and is absent with it off.*
5. **Streamable HTTP** transport + bearer auth — *done when Anthropic's API MCP connector (`mcp-client-2025-11-20` + paired `mcp_toolset`) reaches `rag_query`.*
6. `answer-eval` pass + README section (third entrypoint) + codemap/LEARNINGS.
